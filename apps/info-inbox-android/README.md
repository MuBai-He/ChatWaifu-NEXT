# 信息收件箱 Android

独立 Gradle 模块，复用 Runtime 的信息整理、知识同步与图检索接口。业务库为 App 私有 SQLite；微信原文归档与 Root 配置留在手机。

## 0.6.7：确认先提交，后续后台处理

持续协助中的确认、修改、核对及委托控制，先保存在原有本机提交队列，立即显示等待宁宁接收；网络请求与界面提交分开，已有待处理记录和可阅读内容保留。刷新优先使用同一连接、会话和分页的缓存，连续刷新合并；提交中的同一事项避免重复点击。手动记忆确认也使用独立的本机保存线程。

服务端先返回已受理的事项记录，任务准备、补查、外部修改、回读和反馈在后台继续。实际任务保存后才提供任务关联；队列繁忙保留提交，不需要手机等待整个执行过程。原文、离线编辑和设备提醒继续保留在手机。

本版本需要与完整 Runtime 的处理权交接区分：当前生产尚未切换完整框架，旧路径仍由手机组织分析批次、服务器运行模型。手机不在身边时只完成源码与构建验证，不记作已安装或实际手机提速通过。

后续小米 14 Pro 原位升级验收已完成：正式签名 0.6.7，schema 6→8，25 张原表的内容与行数一致；受控网络阻塞下确认反馈单次 55 ms，关闭重开补交通过。离线本地提醒在与正式版一致的后台豁免条件下通过 34 项；临时包默认限制下首轮延期记录保留。全部结果与范围见统一验证记录，不代表正式服务器已完成接管。

## 0.6.3：批量保存与 SQLite 并发（2026-11-01）

同一进程按数据库文件共享 SQLiteOpenHelper 和 WAL 连接池，各使用者按计数释放自己的引用；关闭页面不会关闭其他后台任务仍在使用的资料库。写事务使用非独占方式，读取预览不再申请写事务。WAL 仍只允许一个写者，连接池负责本进程内的写入排队，不新增 AI 状态机或无界写入队列。

最多 100 条的批量确认仍为一个原子事务，任何一条失败都整体回滚；预览、选择快照、出处、修订和权限检查保持，真正提交前重新核对。嵌套保存不调用同步调度或前台服务，最外层提交后统一唤醒一次同步。临时数据库锁单独标为 storage_busy，保留来源与租约恢复，不消耗模型失败次数。

103 项原生单元回归通过，Debug/Release 构建与双 Lint 通过。手机隔离资料库 storage_only 验证通过 8 项断言，覆盖写事务占用时预览可读、跨使用者关闭、100 条末尾失败回滚与重复确认拒绝；该小样例成功保存耗时 306 毫秒，不包括网络同步和界面重绘，也不是任意资料规模的延迟承诺。schema 仍为 6，已有记录与连接配置不改写。

## 0.6.2：分区快照与失败恢复（2026-11-01）

首次打开或手动刷新才重新读取建议、出处和处理队列，当前/历史及内容类型切换复用同一页的已核对快照。缓存只属于当前页面，切换来源或离开页面即失效；新结果仍提示刷新，保存时重新核对出处、修订、当前建议与权限。最多预备五个分区的第一页，不在 UI 线程重新读库或解析出处。

“当前”不是最近消息筛选。记忆和资料按内容类型展示，可来自较早但仍有价值的原文；“事项”只列当前有效的未确认待办/日程；过去或当前有效性不明的任务位于“历史”。页面内有相同说明。

失败资料显示段数与最近失败的可读原因。新记录区分模型格式/出处错误、模型不可用、连接中断/超时、接入校验与来源版本变化，错误消息不包含原文或模型响应。服务器在现有预算内对结构错误最多补正一次，仍失败则保留进度，不把失败标成成功。恢复只重试失败段，不重新整理已完成历史。

## 0.6.1：历史事项与当前待办分开（2026-11-01）

AI 建议分为“当前、记忆、资料、事项、历史”。原文发送时间保持原样；本次整理时间仅帮助判断现在是否仍需处理，不能拿来解释原文的“明天”。

未确认事项按照原文证据评估时效：已过去的活动进入历史核对；超过七天且没有明确未来安排的旧承诺，标记为是否仍需处理待核对。有明确未来时间的安排与最近提及的逾期待办继续保留。这里的七天沿用近期采集窗口，只是保守核对边界，不代表完成、删除或保存期限。已确认的记忆、待办和提醒不因这个判断被修改。

已有待核对建议读取时重新分区，原始建议与出处无需批量改写或重新调用模型。历史分区按原文时间排列，可查看出处、忽略或逐条“确认仍需处理”；通用批量保存不会重新激活历史任务，提交时会再次检查。Runtime 管理的未确认历史事项也不能从持续委托重查中自动获得执行权。日期型截止与全天活动的日期保持独立，不猜钟点。

## 0.5.9：历史顺序、并行整理与历史背景（2026-10-30）

“连接暂未完成”来自全量处理中的同步读超时，旧状态又未随阶段恢复刷新；连接凭据与会话保留。
现在知识库同步使用原有独立任务，AI 整理继续推进，阶段、同步重试和整理失败分别反馈。
手机与 Runtime 最多同时处理 4 个会话，同一会话只允许一个批次；完成即补充后续任务，成功批次不再固定等一分钟。

在“AI建议 → 处理状态与更多操作 → 全量历史处理”选择“从最早历史接着整理”，
也可“切回新消息优先”。已有完成进度保留；按会话核对归档里更早但尚未入队的消息，再继续较新的批次。
较早批次需要重试时，后续同会话等待，其他会话继续。暂停与恢复保留进度，迟到任务受意图版本和租约检查。

后续整理会带入同会话、原消息时间更早的已确认记忆和标明待核对的历史摘要。
背景不成为新进度或写入权限，原文引用和来源版本继续保留；快照发生更改、排除或遗忘时重新核对。
每次最多 10 条背景、6,000 UTF-16 单元，连同当前证据总出处最多 30 个；超出时跳过相应背景并提示上下文不完整。
旧摘要仅作参考，完整历史不会一次性放进模型，保存仍由用户确认。原有存储版本和整理模型保持不变。

86 项安卓用例、24 项生产兼容接口用例、严格类型／Ruff、Release 构建和 Lint 通过。
真实模型的一组合成“旧约定改期、待核对猜测不能覆盖新原文”通过，仅生成建议。

## 构建

需要 JDK 17、Android SDK 36 / Build Tools 36.0.0；通过 `ANDROID_HOME` 或未入库的 `local.properties` 指定 SDK。

```sh
cd apps/info-inbox-android
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
python3 -m unittest discover -s tests/python -v
```

Debug 默认使用本机生成的开发签名。正式升级现有手机时，通过 `INBOX_SIGNING_KEY` 指向原签名文件，并设置对应的 `INBOX_SIGNING_PASSWORD`、`INBOX_SIGNING_ALIAS`、`INBOX_SIGNING_KEY_PASSWORD` 和 `INBOX_SIGNING_STORE_TYPE`；默认值兼容现有本机 PKCS12 开发签名。签名文件及密码保留在本机或 CI Secret 中。未配置签名时 Release 产物为未签名 APK。

```sh
./gradlew :app:assembleRelease :app:lintRelease
```

首次使用需要本人手机已有经验证的 Root 采集配置；本模块不包含微信账号、数据库密钥或聊天数据库。仓库内 Root 运行库的来源和许可见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。新手机配置、Root 授权、通知和提醒权限需要真机验收；CI 不读取微信或提交真实资料。
