# 宁宁统一 Agent Harness：消息、记忆、工具与持续行动

日期：2026-10-31（Asia/Shanghai）。状态：完整方案已由主人授权实施，源码已整合并通过阶段验证，但仍有普通确认入口、无绑定事项续办、处理权交接等实现缺口；完整 Runtime 尚未切换到生产。2026-11-01 按原计划登记 30 项交付缺口，详见验证记录末尾“原始完整方案缺口审计”；决策见 ADR 0085。

2026-11-01 后续：基线与第一批缺口修复分别经 PR #85、#86 合入 main；范围内确认续办、处理归属、失败核对、通知恢复和原文时间已进入主线。默认提醒、只读补查和大数据交接继续隔离实施，详情以验证记录的后续批次为准。30 项最初登记保留审计快照，源码验证不等于生产或实机验收。

本提案回答两个问题：微信消息整理之后目前会发生什么；怎样让聊天、微信观察、记忆整理、日历和后台跟进成为同一个宁宁的完整工作循环。

实施前调查说明：调查依据为当时 CW2 工作区源码（包括已有未提交改动）、既有设计与官方项目文档；该调查没有读取真实微信内容或修改真实日历、提醒、账户、生产配置。外部项目比较属于文档研究，未安装运行它们，不声称性能或可靠性胜过 CW2。后续实际实施、真实资源验收及当前缺口以验证记录中各阶段的事实为准。

## 已确认的实施选择

- 范围授权后自动执行，敏感或不明确事项才核对。
- 记忆按来源、冲突和敏感性分级接受，保留人工确认身份。
- Runtime 统一编排，手机保留采集、原文、离线编辑和本地提醒。
- 迁移已确认记录，重评待确认与未处理历史，不全历史重跑或追溯执行。
- 重要变化及时通知，普通保存静默，其他正常动作合并摘要。
- 沿用现有内核和 SQLite，不引入另一套工作流引擎。

实现与验收事实见 [验证记录](../operations/unified-agent-harness-validation-2026-10-31.md)。第 2–3 节保留实施前调查快照，不代表实施后源码仍缺少这些路径。当前实现、验证与切换边界以验证记录和 ADR 0085 为准；目标连线不能替代实际验收。

## 1. 结论与建议

当前 CW2 已具备一套统一 Agent 系统的大部分基础组件：角色、模型路由、正式记忆、个人知识、能力发现、Runtime Skills、持久任务、日历适配器和提醒投递。缺口主要在输入事件、持续委托、上下文、领域对象和执行回执之间的连接。

推荐重构为**一个 Runtime 内的共享 Agent 执行内核，加上持久事件与任务层**。聊天、新微信、资料确认、日历变化和到期跟进通过不同入口唤醒同一执行体系；角色、记忆入口、工具权限、行动账本和结果表达保持一致。

不建议把“提取出 event 就直接调用日历 API”作为最终方案。它会绕过来源修订、用户意图、重复事项匹配、取消/改期、外部写入查证和后续跟进。提取结果应产生有来源的观察或候选，再由已授权的行动流程处理。

也不建议因为愿意重构就立即替换整个产品为某个通用 Agent 项目。CW2 已有实时语音取消、主人/群隔离、来源和遗忘、设备提醒及工具执行语义。替换框架必须证明能继承这些行为，而不只是跑通一次工具调用。

## 2. 目前整理完成后的真实链路

| 环节 | 当前行为 | 边界 |
| --- | --- | --- |
| 微信提取完成 | 建立待确认建议，并把已处理消息推进到完成状态 | 不直接创建正式记忆、外部日历或 Agent 任务 |
| 确认记忆/决定/资料 | 手机保存本地记录，进入知识同步路径 | 手机“记忆”不等同于 Runtime 正式人格记忆 |
| 确认日程/待办 | 写入本地 work_items，并保存来源和变更版本 | 这里的 event 是手机事项，不自动等于 Google/Apple 日历事件 |
| 设置提醒时间 | 保存提醒规则，由 AlarmManager 安排本地通知 | 通知权限、精确闹钟权限和设备运行状态影响交付 |
| 确认改期/完成/取消 | 更新事项版本，重建或撤销对应提醒 | 当前仍经过确认入口 |
| 知识同步 | 同步来源、已确认对象、政策和修订，驱动知识索引 | 没有发现同步完成后创建日历操作或 Agent 任务的调用链 |
| 宁宁查询个人资料 | 通过 knowledge.search 获得带版本和出处的资料 | 只读检索不会自行创建提醒 |
| 用户直接要求安排事项 | 聊天可发现并调用日历、待办、提醒工具 | 受工具权限、目标账户和确认策略约束 |
| 已明确交办的持续任务 | AgentTaskService 可调用工具、记录步骤、等待、恢复和验证完成 | 微信整理结果尚未进入这条任务入口 |

可核对的源码：

- [AnalysisEngine](../../apps/info-inbox-android/src/com/mubai/infoinbox/AnalysisEngine.java)：runBatch 组织取材、调用整理和提交结果。
- [PersonalInformationService](../../services/runtime/src/chatwaifu_runtime/information/service.py)：第 134 行起只调用提取模型、校验并返回建议。
- [OrganizerStore](../../apps/info-inbox-android/src/com/mubai/infoinbox/OrganizerStore.java)：finish 第 641 行起保存待确认建议；confirm 第 923 行起写本地事项与提醒。
- [ReminderScheduler](../../apps/info-inbox-android/src/com/mubai/infoinbox/ReminderScheduler.java)：第 48 行起调度，第 196 行起连接确认、提醒核对和知识同步。
- [KnowledgeSync](../../apps/info-inbox-android/src/com/mubai/infoinbox/KnowledgeSync.java)：第 31 行起同步；同步开关与后端连接仍是前提。
- [知识同步仓储](../../services/runtime/src/chatwaifu_runtime/persistence/sqlite_knowledge.py)：第 125 行起应用版本化变更与回执。
- [KnowledgeSearchSkill](../../services/runtime/src/chatwaifu_runtime/knowledge/skill.py)：只读、主人私有的知识检索。
- [AgentTaskService](../../services/runtime/src/chatwaifu_runtime/agent/tasks.py)：第 603 行起复用 AgentTurnOrchestrator 执行、检查证据并有界修复。

因此，对“整理后是否会触发日程”的准确回答是：**确认后已有本地事项和提醒；自动转换成外部日历操作、宁宁自主跟进的通用闭环尚未接通。**

## 3. 已有能力应保留，缺口应明确

### 3.1 重要的既有基础

AgentTaskService 已有任务授权、预算、检查点、步骤去重、等待唤醒、重启恢复和未知写入处理。它内部使用与聊天同类的 AgentTurnOrchestrator，并通过 context_builder 获取角色与记忆。不能把它描述成“还没有任何后台 Agent 能力”。

RuntimeSkillService 已承担能力注册、权限、确认、超时、取消和审计。CapabilityCatalog 支持发现、检查和激活能力。日历、知识检索、工作区等应继续走这一条执行入口。

SQLite 知识层已保存版本、来源、同步冲突和操作回执；Graphiti/Neo4j 是可重建的派生索引。正式记忆有独立的筛选、冲突、隐私和遗忘规则。这些约束比框架名称更有价值。

相关决策：[ADR 0078](../adr/0078-autonomous-agent-tasks-and-group-decisions.md)、[ADR 0084](../adr/0084-personal-knowledge-map.md)、[ADR 0055](../adr/0055-personal-calendar-cache.md)。

### 3.2 当前缺口及影响

| 优先级 | 缺口 | 实际影响 | 建议处理 |
| --- | --- | --- | --- |
| P0 | 微信来源/整理变化没有进入统一任务触发入口 | 有知识，但不会因新通知主动采取后续行动 | 增加持久观察与消费游标，接入既有任务系统 |
| P0 | 单次任务授权尚不能表达可持续运行的个人委托 | 每次需要重新交办，或容易把一次授权错误扩展成长期权限 | 增加版本化 StandingIntent，与每次运行分离 |
| P0 | 手机事项、外部日历、服务端提醒缺少统一关联身份 | 同一件事可能重复建立、改期只改一端、提醒重复 | 增加逻辑事项与外部绑定，明确字段权威方 |
| P0 | 周期日程实例修改被当前适配服务明确拒绝 | “本周课程临时改时间”不能仅靠开启 Agent 实现 | 增加实例级操作与验证；系列修改另设明确范围 |
| P1 | 信息提取只用预先拼好的上下文 | 代词、旧约定、跨消息修正可能缺证据 | 提供按需只读补查，再决定提取、行动或澄清 |
| P1 | 背景执行能力语义仍偏布尔标记 | “异步技能”“无人值守执行”“持久任务”难以精确区分 | 增加执行模式与授权上下文，逐项审核现有技能 |
| P1 | 日历操作缺少统一的领域完成验证 | 成功话术或工具返回值不能证明正确实例、正确时间已生效 | 由对应适配器执行确定性回读检查 |
| P1 | 整理完成、处理完毕、动作完成、送达状态容易混淆 | 用户不知道宁宁只是读过，还是已经安排并提醒 | 建立各自状态与端到端可解释记录 |

周期事件限制的直接证据是 [accounts.py](../../services/runtime/src/chatwaifu_runtime/personal_assistant/accounts.py) 第 208–235 行：带 recurrence、recurring_event_id 或特殊 event_type 的修改/删除会返回 complex_event_edit_not_supported。这是现有明确能力边界，不是已复现的数据损坏问题。

还有两个应在重构时解决的细节：

- [agenda_skill.py](../../services/runtime/src/chatwaifu_runtime/personal_assistant/agenda_skill.py) 第 102–107 行为 create 生成新的 uuid4。它不是可以跨任务、跨重试复用的业务行动 ID。现有 TaskGateway 已能复用同任务的已知成功步骤，但不足以替代跨触发的事项去重与供应商级幂等设计。
- [verification.py](../../services/runtime/src/chatwaifu_runtime/agent/verification.py) 对工作区写入有确定性的路径/哈希回读检查，其他完成判断主要交给模型结合账本。建议扩展领域验证接口，不把日历验收塞成更多工作区式硬编码分支。

技能清单中的 background_allowed=false 不能直接推导“所有持久任务都不能调用它”。[RuntimeSkillService](../../services/runtime/src/chatwaifu_runtime/runtime_skills/service.py) 检查的是 invocation.background；任务网关另带 task_id 授权。重构必须先统一这两类语义，不能仅把几个 false 改为 true。

## 4. 其他系统的做法与可借鉴部分

以下是截至调查日读取到的官方文档所描述的行为；不把文档支持能力当作已经在 CW2 验证。

| 项目 | 官方设计中与本任务有关的部分 | 对 CW2 的启发 |
| --- | --- | --- |
| OpenClaw | 持久调度由 Gateway 执行；Standing orders 描述持续职责；Standing intents 区分事件触发的未来意图和时钟任务 | 把职责、唤醒、执行、交付分开；新消息只是触发条件，不是授权 |
| Hermes Agent | 定时任务可启动新 Agent 会话，也可运行不经 LLM 的脚本；执行账本区分 completed、failed、unknown | 简单到点提醒无需模型；运行与交付分别记录；未知结果不要盲目重跑 |
| LangGraph | Checkpointer 保存单次线程执行状态；Store 保存跨线程信息；interrupt 可持久等待外部输入 | 共享记忆与共享运行状态是两回事；澄清与确认应能跨重启恢复 |
| Deep Agents | 在 LangChain/LangGraph 上组合规划、上下文管理、工具、记忆及可选委派 | Harness 是一组协作能力，不只是一个 LLM 循环；可以采用组件而不整体移植 |
| Letta | 当前 Memory & dreaming 文档使用可编辑的 MemFS，后台整理记忆；共享仓库可与会话生命周期分离 | 对话可以不同，长期知识仍共享；记忆巩固可放后台，不能拖慢实时回复 |
| Temporal | 持久定时器恢复后可继续；外部动作通过 Activities 执行，并要求考虑幂等重试 | 数小时后的跟进不能仅靠内存 sleep；工作流恢复不等于外部副作用恰好执行一次 |

来源分别为 [OpenClaw Automations](https://docs.openclaw.ai/automation/cron-jobs/how-it-works)、[Standing orders](https://docs.openclaw.ai/automation/standing-orders)、[Standing intents](https://docs.openclaw.ai/concepts/standing-intents)、[Hermes Cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)、[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview)、[Letta Memory](https://docs.letta.com/configuration/memory)、[Letta Shared Memory](https://docs.letta.com/agent-sdk/repositories)、[Temporal Timers](https://docs.temporal.io/develop/python/workflows/timers)、[Temporal Activities](https://docs.temporal.io/activities)。

需要避免两类误读：

1. OpenClaw 的事件型 standing intents 文档描述的是符合条件的交互轮次匹配，不代表它自动监控所有外部来源。CW2 仍须实现微信观察适配器。它的 Markdown 委托表达可以借鉴，但 CW2 的可执行权限应落到已有的结构化授权系统。
2. Letta 当前共享仓库 SDK 文档的相应 API 要求 cloud 后端；V1 blocks 在其文档中归入 legacy。这里借鉴共享知识与后台巩固的分工，不把旧版 blocks 与新版 SDK 当成同一部署方案。

Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 区分固定工作流与模型决定步骤的 Agent，并强调依据真实环境反馈继续执行。文章发表于 2024 年，页面也提示工具生态已变化；本提案只引用其架构原则，不将旧框架清单当作当前选型依据。

## 5. 推荐的目标结构

~~~mermaid
flowchart TD
  A[微信增量 / 聊天 / 日历变化 / 到期事件] --> B[可信输入适配器与观察收件箱]
  B --> C[来源版本、范围、去重与触发策略]
  C --> D[宁宁共享执行内核]
  D <--> E[统一上下文入口：正式记忆 / 个人知识 / 当前事项]
  D <--> F[能力目录与 Runtime Skills]
  F --> G[当前授权与行动账本]
  G --> H[日历 / 待办 / 提醒 / 其他适配器]
  H --> I[领域回读与结果核验]
  I --> J[对象状态、行动回执与交付]
  J --> K[后续事件或持久定时唤醒]
  K --> C
  I --> L[带来源的记忆候选]
  L --> E
~~~

这个图描述目标，不代表这些连线当前全部实现。

“同一个宁宁”应具体落实为共享角色身份、主人范围、知识入口、能力目录、授权与行动记录。它不要求共享一个不断增长的聊天上下文，也不要求所有任务使用同一个模型。

建议保留四种执行模式：

| 模式 | 主要任务 | 执行约束 |
| --- | --- | --- |
| interactive | 即时聊天、按请求用工具 | 优先保证响应和 generation 取消语义 |
| observe | 新消息理解、相关性判断、候选提取 | 默认为只读；允许有预算地补查 |
| act | 已授权的创建、修改、跟进 | 持久任务、行动账本、写前检查、写后验证 |
| consolidate | 记忆去重、摘要更新、冲突整理 | 低优先级；不得自行扩大权限或产生外部动作 |

这些是运行配置，不是四个各自拥有记忆和权限的新 Agent 服务。简单消息仍可以单次提取；复杂消息才进入补查与工具循环。宁宁有权选择不行动、等待更完整的消息、提出关键澄清或安排后续检查。

## 6. 应统一的数据与契约

### 6.1 身份与执行上下文

扩展现有 AgentEvent、AgentTask、TaskAuthorization，先做兼容适配，避免另建一套等价类。

执行上下文至少表达：

- 主人、角色、入口渠道、受众范围。
- execution_id、task_id，以及交互场景已有的 session_id、turn_id、generation_id。
- 触发来源、来源修订、授权 ID/版本、当前政策版本。
- 执行模式、工具/模型/时间预算、可用交付端。
- 取消与暂停状态、关联的逻辑事项和上一轮检查点。

不能通过客户端传入 owner_id 或来源文本来授予权限。主人身份、受众和授权由可信边界派生。后台工作应归属持久主人/角色范围；聊天 session 是交互入口，不能让关闭一个窗口意外撤销持续委托。

### 6.2 观察记录

建议 Observation 记录包含 source_ref、revision、conversation/account scope、event_time、received_at、ingestion_mode、source_kind、policy_epoch、correlation_key 和短摘要引用。

必须区分：

- 历史回填：补全知识，不自动补执行过去的承诺。
- 实时新增：可以进入当前行动判断。
- 延迟同步：结合事件发生时间和事项现状决定是否还有效。
- 编辑/撤回/取消：使旧观察和未执行计划失效，已执行事项进入核对流程。

不能只用“比现在早多少分钟”区分历史与新增。采用采集模式、首次观察标记、同步游标和来源时间共同判定。手动要求处理历史时，仍需另行确认哪些历史事项现在有效。

### 6.3 四种状态不能混为一种完成

| 状态维度 | 含义 |
| --- | --- |
| 采集/同步状态 | 消息是否到达、版本是否同步 |
| 理解状态 | 是否完成取材和提取，是否仍缺关键上下文 |
| 事项状态 | 拟议、已确认、进行中、已改期、已完成、已取消 |
| 执行/交付状态 | 动作已计划、执行中、待查证、已验证，以及结果是否送达 |

现有 processed_refs 继续表达本批处理进度，但不能作为后续动作已经完成的证据。空 items 允许表示没有可提取建议，同时应记录本次观察的处理结论；对高价值而证据不足的消息，应能明确标为 needs_context，而不是无声地与“无关消息”合并。

### 6.4 共享记忆采用统一入口与分层存储

建议通过 ContextService/MemoryFacade 暴露按需检索：

| 数据 | 权威与用途 |
| --- | --- |
| 原始来源 | 手机原文与已同步的不可变版本；作为证据 |
| 知识候选 | 模型解释、待核对关系；保留不确定性 |
| 正式记忆 | 经现有记忆策略接受的事实、偏好和共同经历 |
| 当前事项 | 日程、待办、等待对象、截止时间；随现实变化 |
| 持续委托 | 用户希望宁宁持续负责什么；与普通记忆分开 |
| 执行记录 | 实际做过的动作、供应商回执、核验和交付结果 |

统一检索接口不意味着把所有数据放进同一表或同一向量库。按问题检索并保留类型、来源、确认状态、有效时间和权限范围。第三方聊天内容不能因为被摘要或索引就升级成主人指令；“模型认为已完成”也不能成为真正执行的证据。

记忆写入仍经过现有 policy/dedup/conflict/privacy/forgetting。微信个人资料可供推理；要升格为正式记忆，须经过同一政策入口。共享不应导致群聊读取主人私有记忆。

### 6.5 逻辑事项与外部绑定

为同一现实事项建立稳定 work_item_id，并将各系统记录绑定到它：

    work_item_id
      -> source refs + revisions
      -> Android local item
      -> provider/account/calendar/item/instance identity
      -> reminder occurrences
      -> action receipts and follow-up runs

这是统一关联身份，不是宣称 Runtime 可以覆盖 Google 的真实日历状态。建议延续 Google/Apple 作为其原生对象的权威来源，Runtime 保存已验证快照、意图、关联和冲突；纯本地事项由本地/同步契约定义权威方。

手机离线编辑保留 base_revision，恢复联网时做版本检查。模型不能仅按标题相似就合并两个事项。匹配不唯一时保留候选或澄清；不能复制一份新日程来掩盖没有找到旧日程的问题。

## 7. 统一触发、授权与执行

### 7.1 事件与定时调度

在来源或已确认对象事务提交时，原子写入事件 outbox。消费者使用幂等键、持久游标、租约和重试状态。模型与网络调用在事务之外执行。

知识索引和行动判断分别消费变化，各自保存进度：图谱索引慢或不可用时，不能阻塞有时效的日历处理；行动也不能跳过原文和政策检查。

优先顺序建议为当前交互、临近截止/新变化、普通跟进、历史整理/记忆巩固。每类都有并发和预算，避免历史任务饿死，也避免历史回填占满模型吞吐影响聊天。新来源合并窗口和超时属于可配置产品参数，先用实际延迟与漏处理数据校准。

时间触发采用持久截止时刻/计划；事件触发依赖来源变化。周期检查只作兜底对账。没有新变化、到期工作或明确复查理由时，不调用 LLM，也不向用户发送“暂无变化”。

复用现有 AgentTaskService 的 wake 和事件去重能力。若现有实现不能承载统一调度，则替换其调度内部；不再平行增加一个只懂微信的定时器。

### 7.2 持续委托

建议 StandingIntent 独立保存以下信息：

- 目标，例如“跟踪选定课程群的调课通知，维护我的课表”。
- 允许观察的来源、允许操作的账户/日历/列表。
- 允许的动作、需澄清的条件、可自动执行的范围。
- 有效期、暂停/撤销状态、版本、费用和频率预算。
- 反馈偏好、静默时段、等待条件、最大重复提醒次数。

长期委托由主人建立；运行任务只能引用和收窄它，不能自行创建更大权限。每轮任务有有限预算，委托可以长期存在。现有任务 Skill 默认 24 小时授权不应直接被改成无限期运行。

授权可以一次设定后持续生效：已授权范围内的读操作、明确的个人事项修改自动执行；来源不明确、目标不唯一、扩大范围、外发消息或更改整个日程系列时按策略澄清。不是把所有动作都变成一次弹窗，也不是把一句“全自动”解释成任意操作许可。

OAuth 决定服务能访问哪些数据，Runtime 委托决定宁宁能在什么情况下自行操作。二者分别验证。

### 7.3 思考与执行的交界

模型可以决定补查什么、选择什么能力、提出什么动作和为什么等待。可信代码验证目标、来源、授权和版本，并负责实际执行。

建议按需要产生 ActionProposal：

    action_id + work_item_id
    operation + target binding + expected version
    source refs + revisions + authority version
    proposed change + explanation
    verification plan + follow-up condition

这不是要求每句闲聊都生成一个复杂计划。只有涉及外部效果或跨轮持续工作的步骤才需要持久化行动记录。

所有写操作继续经 Runtime Skills。插件/MCP 能力应有一致的执行上下文、超时、错误、取消和副作用分类；能力发现本身不改变权限。

### 7.4 幂等、未知结果与取消

外部请求不能承诺普遍的 exactly-once。现实目标是可恢复处理、尽可能幂等的动作、明确未知结果及不会盲目重放。

- source event/consumer/policy version 防止同一输入重复触发。
- work_item/operation/expected revision 防止不同消息再次执行同一变更。
- action_id 在重试、重启和工具适配间保持稳定；供应商支持时用作幂等键或客户指定 ID。
- 请求发出但回执未保存：进入 outcome_unknown，先按外部 ID/动作标记回读。
- 已知未产生效果的失败可以有界重试；结果未知不应直接再创建一次。
- 读取后出现人工修改：CAS/etag 冲突，重新读取并判断，不覆盖用户新改动。
- 在外部提交边界前检查撤销和来源版本；请求已经发出后无法保证远端取消，应记录竞态并查证结果。
- 补偿是新的、有授权的操作；不要把“撤销来源”机械等同于删除已经建立的真实日程。

LangGraph 的 interrupt 文档也明确指出，恢复节点可能重执行前置代码，因此副作用仍需幂等或拆到独立步骤。使用框架不能消除此要求。

## 8. 日历和提醒要补齐的具体能力

### 8.1 事件实例

单次课程应使用 provider/account/calendar/series/occurrence identity 关联；Google 的 recurringEventId 与 originalStartTime 能表达系列及原定发生时刻。

明确区分 this_instance、this_and_following、entire_series。第一阶段实现普通事件与 this_instance；后两种在工具 schema 中明确返回暂不支持，直到具备完整的供应商操作和回滚方案，不能把整个系列删除后重建当作默认捷径。

官方依据：[Google Calendar recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents)。单个实例修改需要定位并更新该实例；修改整个系列或“此后全部”不能按所有实例逐个改来代替。

### 8.2 动作验证

增加领域 VerificationPort，按能力注册，而不是把所有情况写进一个模型评分器：

- 日历创建：回读外部 ID，核对目标日历、开始/结束、时区及关键字段。
- 日历改期：回读目标实例，核对旧实例身份与新时间；确认没有意外修改整个系列。
- 待办完成：回读状态与目标身份。
- 提醒安排：检查持久计划、设备/渠道目标及规则版本。
- 通知交付：区分服务已接受、设备已呈现、用户已确认。不能把前三者自动等同于用户看见。

语言模型可以评估语义完成度和修复方案；它不能代替以上确定性的外部事实核对。未核验状态在用户界面如实显示。

### 8.3 多端提醒

保留手机离线提醒能力，建立统一 reminder_occurrence_id、事项版本和投递策略：

- 默认选定主提醒端和是否允许其他端补充。
- 交付成功、关闭、贪睡、完成均回写；多端共享状态。
- 不承诺离线分区下绝对不重复，明确主端、租约和恢复对账策略。
- 本次 occurrence 的提醒时间来自已确认或已授权的计划，不让模型每次唤醒重新猜。
- 改期或取消后，旧版本提醒失效；已发出的通知可以清除，但不伪造“从未发送”。

Google Tasks 的日期型截止与精确提醒时刻分开表示；当前 AgendaService 已有对此的限制，应继续保留，而不是把任务 due_date 当作闹钟。

## 9. 以调课为例的完整闭环

场景为设计示例，不使用真实聊天或真实课程。

1. 主人已经委托宁宁维护指定课表，来源为所选课程群；不包含向老师发消息的权限。
2. 采集到“本周三第 3、4 节改到周四下午，教室待定”。观察记录保留原文时间、说话人、来源版本和实时新增标记。
3. 轻量判断发现与委托有关；若上下文不足，调用消息原文/知识检索与 calendar.read 查课表。按需查证，不预装全部历史。
4. “周四下午”没有唯一时间。宁宁保存 waiting_input，只问缺少的具体节次或开始时间；不猜一个时刻写入日历。
5. 后续消息补充“第 7、8 节，B203”。新观察关联同一逻辑事项并唤醒原任务，不另建一套重复计划。
6. 找到本周三对应课程实例，读取当前版本、时间和冲突；确定只改单次。
7. 在委托范围内，经工具执行改期并记录稳定 action_id。无需对已经明确授权的普通改期重复索要权限。
8. 回读该实例，确认日期、节次对应时间和教室；重新安排该事项的提醒。
9. 宁宁在用户选定的交互端报告实际结果，提供来源与查看入口。完成结论进入行动记录；适合长期保存的信息再进入记忆候选。
10. 若随后收到“取消调课，恢复原时间”，先核对现有实例是否被用户再次编辑，再决定执行恢复或询问。来源撤销不直接抹除已发生的行动事实。

同一框架还应通过以下不同类型场景：作业截止变化、会议待确认、等待对方回复、资料补充、课前准备、无行动价值的闲聊。场景知识可以放在技能说明中；主调度器不按“调课”“作业”等词编写业务分支。

## 10. 框架选型建议

| 方案 | 本项目收益 | 代价与限制 | 结论 |
| --- | --- | --- | --- |
| 重构现有 CW2 执行内核与持久任务 | 保留已实现的权限、记忆、语音与渠道边界，直接填补观察/行动缺口 | 自行维护状态机、恢复与可观测性 | 推荐主路线 |
| 在后台执行适配层使用 LangGraph | 显式工作图、检查点、可恢复等待 | 与已有任务账本重叠；需界定单一状态权威方，外部幂等仍自负 | 可做有限验证后决定；不同时上线第二个调度器 |
| 使用 Deep Agents 作为执行后端 | 提供上下文、规划和工具组合能力 | 默认能力要经 CW2 权限适配；不直接解决微信来源、日历实例与多端提醒 | 可替换的候选，不作为当前迁移前提 |
| 引入 Temporal | 跨进程持久执行、长等待和多 worker 运维能力 | 增加服务部署及运行成本，与本地 SQLite 基线不同 | 多实例可靠执行成为明确需求时再做 ADR |
| 整体改为 OpenClaw/Hermes/Letta | 获得其产品与生态能力 | 需要重接当前产品、迁移记忆/授权/实时语音/设备语义；部分形态有云端要求 | 当前缺口不足以支持整体替换的收益判断 |

以上是结合 CW2 现状的工程判断，不是外部框架基准排名。

如果后续验证 LangGraph，验证目标必须是减少现有任务状态和恢复代码，同时保留同一副作用账本；不能在外面套一层图，内部照旧运行完整任务状态机，却形成两个“完成”和两套恢复语义。

## 11. 实施顺序与可回退边界

### 阶段 A：冻结契约与最小共用内核

补充 ADR：统一执行上下文、来源/意图/运行分离、外部对象权威方、写操作验证与授权语义。以当前行为为基线，从已有 AgentTurnOrchestrator、AgentTaskService 和 context_builder 提取共用入口。

验收：聊天、现有显式任务的行为不退化；前台 generation 打断不会取消已获授权的后台目标；明确暂停/撤销能阻止后续执行。

### 阶段 B：微信观察入站与影子决策

扩展来源同步契约，增加实时/回填区分、outbox、消费游标和任务关联。先让宁宁记录“会做什么、为什么、引用什么”，不进行真实外部写入。

验收：新消息不会被历史积压阻塞；重复同步只形成一次有效观察；原文修改与撤销使旧决策失效；无关消息保持安静。

影子阶段是验证新行为的发布步骤，不是永久要求每次确认。

### 阶段 C：共同知识与只读工具

让 observe 运行使用统一 ContextService，能查原文、记忆、当前事项和日历。继续保留便宜的单次提取路径，对缺证据的情况才进行有界补查。

验收：“按上次时间”“不是我，是小王”“又改回去了”等场景能查证或明确等待，不产生无依据写入。

### 阶段 D：持续委托与首个完整行动

落地 StandingIntent、授权版本与运行预算；实现普通日历事件及单次周期实例、稳定 action_id、领域回读和反馈。以合成课程和专用测试日历验证后，再按具体授权启用真实目标。

验收：一条新通知能在已有委托内自主完成查证、修改、回读和反馈；重复消息、崩溃和重启不会盲目重复写。关键不确定性才向用户提问。

### 阶段 E：事项身份、双向对账与多端提醒

将手机 work_items、同步 knowledge records、外部日历/待办与提醒 occurrence 绑定到统一逻辑事项。保留旧 ID、来源链和离线修改；补齐冲突显示与处理。

迁移先建立映射，核对旧、新投影，再按事项/来源切换单一写入权威。避免新旧两个调度器同时对同一事项产生效果；回退停新触发并核对在途动作，不删除既有外部日程。

验收：手机离线改期、Google 手动修改、提醒贪睡与完成在恢复联网后可解释、无静默覆盖。

### 阶段 F：统一交互与通用场景

共享网页/桌面行动时间线，安卓显示同步后的同一状态。补齐对话中的暂停、继续、纠正与查询进度。验证待办、等待回复、冲突提示等场景走相同工具和任务入口。

验收：用户能问“你为什么改了这个”“现在在等什么”“暂停课程自动处理”，并得到来源、真实状态与有效控制。

### 阶段 G：合并重复执行路径

在前述闭环验收后，再决定删减手机端重复的业务编排、废弃旧后台模式标记、统一提醒投递和模型上下文构造。直接模型接口如继续保留，应清楚限定其独立模式能力，不能宣称拥有 Runtime 的共同记忆或授权工具。

不在第一批同时重写 Android UI、所有存储、语音栈和 Agent 内核。允许架构重构，但每一批必须有完整可验收行为及回退位置。

## 13. 验收场景与度量

复用已有测试与临时数据库、假供应商。只有真实行为缺口才增加用例，不新增与实现一一对应的镜像测试工程。

| 场景 | 必须证明的结果 |
| --- | --- |
| 同一消息同步三次/同一通知被转发 | 不重复创建同一行动；不同来源证据可合并 |
| 历史导入与实时通知同时到来 | 历史不补执行过去动作；实时不被积压饿死 |
| 输出合法但内容漏提/主体误判 | 语义评估能识别，不能只以 schema 通过计成功 |
| 提取期间源消息变化 | 旧结果不能提交为当前计划 |
| 行动前撤销委托/排除来源 | 不再发起动作；在途远端结果进入查证 |
| 等待用户补充后重启 | 恢复同一任务与问题，不丢上下文、不重新问已答信息 |
| 外部写成功但回执丢失 | 先回读，对同一目标查证；不盲目再创建 |
| 读取后被用户改动 | 版本冲突，不覆盖新改动 |
| 改周期课程单次实例 | 只改目标实例；其他周次不变 |
| 日历确认后手机离线 | 已保存的本地提醒仍工作；联网后对账 |

### 确认的响应边界

确认采用“持久提交后返回”：手机先保存轻量确认决定和操作 ID，后台同步到 Runtime；Runtime 保存命令后返回受理状态，任务准备、模型补查、日历写入、回读和交付继续在原任务系统处理。界面区分本机待提交、服务端已受理、正在处理、已完成及需要核对。task_id 只引用已实际保存的任务；等待准备阶段以事项和操作 ID 查询。网络慢、关闭页面或重复请求不会要求手机一直等待，也不会重复外部效果。原文、离线编辑和设备提醒继续留在手机。
