## 调查依据

上一轮来源核对后，Raft 回答仍出现技术错误，且没有外部读取。检查实际请求发现：
技术问题最初没有得到 web 工具 schema，因为技能检索描述未覆盖协议、算法或 API。

均为 3.8 Flash High。Raft 的三次初始请求实际均带两个来源工具，`tool_choice=auto`：

- r0/r1 仍直接回答，没有读取；对每次计时器重置重新随机化的说法过强，r0 还把
  `[T,2T]` 及时间举例归为规范要求。仅提供工具或增加可选提示没有解决问题。
- r2 搜索命中原始 Raft PDF，随后 `/md` 返回 500。Runtime 如实给出未核实答复，
  没有把搜索片段当成功原文，但用户技术问题未获解答。
- 三份充电宝规则和三份后续清单保留实际 CAAC 来源、容量分档、3C 与召回限制。
  本轮读取的基础页正文确实有 ≤100Wh 分支。不能把提及审计 3/3 当作全部现行
  规定、完整 presentation 或整个 Q02 已通过。

reasoning 43/45 报告，已知小计 33258，完整总量未知；CLI 的逻辑回合小计 31496

## 修改方案与边界

1. 保留普通解释的自动工具选择。对当前用户明确询问协议、算法或 API 的时序、约束、
   保证等规范问题，要求先获得工具结果；不使用算法名称、参考答案或模型回复做路由。
   明确不联网及给定代码/规范片段的分析不触发这一新增要求。已有权限网关仍可拒绝，
   拒绝后不得交付未核实草稿。
2. 服务器部署的是 Crawl4AI 0.9.2，其 `/md` 实现固定使用网页浏览器与 HTML 提取策略；
   部署镜像还缺少 `pypdf`，实际初始化 PDF 策略返回 ImportError。PDF 失败不能全归因于
   模型。上游 [0.9.3 changelog](https://github.com/unclecode/crawl4ai/blob/main/CHANGELOG.md)
   和 [PDF 文档](https://docs.crawl4ai.com/advanced/pdf-parsing/)说明 Docker 的策略配对
   与 PDF 支持修复。先在独立 `127.0.0.1:11236` 验证 0.9.3，不原地替换运行服务。
3. Runtime 对 `.pdf` 路径使用固定 `/crawl` PDF 策略，网页继续 `/md`。PDF 解析留在
   独立 Crawl4AI，不给 Runtime 安装 PDF/浏览器 SDK，不开放任意策略、hooks、图片
   写入路径。验证单个成功结果、原 URL、状态和实际正文；保留认证、公网验证、字节
   限制及取消。扩展名以外的 PDF 和 OCR 不在本次支持范围。
4. Reader 独立的 6000 字片段上限保持明确，提示字面 focus 要使用原文语言；未匹配
   或被裁剪的章节必须补读后才能据此断言。评测器 1.20.0，来源回合保守上限由实际
   循环推导为 12，计入工具、纠正、草稿和一次核对，不再把 6 当作完整请求上限。

## 独立 HTTP 规范问题暴露的章节定位问题

额外加入未用来编写规则的 HTTP PUT/POST 幂等性四轮场景，仍使用 3.8 Flash、
生产 SearXNG/Crawl4AI 和同一模型预算。v4 的第一轮确实进行了搜索和原文读取，
但 `focus="9.2.2. Idempotent Methods"` 未匹配带链接的 Markdown 标题：
677297 字的原文只返回开头 6000 字，`text_offset=0`、`focus_matched=false`。
模型之后的未交付草稿仍错误泛化 POST 自动重试要求。第五个 Provider 回合发生
RuntimeError，整轮未交付、完成计数为 0；只记录错误类型，具体服务端/解析原因
尚未确定。五次尝试的用量仅有四次完整报告，不能忽略失败调用或算作零成本。
失败批完整保存在 [http-holdout-v4](q02-server-deployed-vs-jina-2026-10-03/http-holdout-v4/)。

随后修正外部 Markdown 的字面 focus：优先正文标题，匹配时去除标题内链接语法，
跳过代码围栏里的示例标题；保留实际正文、原来的清理规则、字符偏移、哈希和
6000 字片段上限。没有语义检索、额外模型调用或扩大总预算。新能力版本 1.4.3、
评测器 1.21.0，使用新输出目录，不混入 v4。
