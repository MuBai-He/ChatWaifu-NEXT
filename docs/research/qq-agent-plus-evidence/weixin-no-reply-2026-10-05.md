# 微信未收到回复：2026-10-05 诊断

范围：今天重新扫码的 CW2 微信私聊；当前聊天模型为 `claude-opus-4-6-thinking`，模型路由和消息短回复提示词沿用现有配置。本次不改变 Q02 的质量验收标准。

## 已确认的现象

- 用户确认“你好”和随后“原神启动”均未在手机上收到回复，且使用的是今天新扫码的对话。
- “你好”在北京时间 06:28:09.871 被 Runtime 接纳；Opus 于 06:28:13.214 完成“又来了……”；微信发送请求于 06:28:13.461 返回，耗时 222.736 ms。生成、渠道轮次和发送部件没有记录错误。
- “原神启动”在 06:35:23.102 被接纳，生成“这次不上当了，我才不会认真接话呢。”，也被原实现标记为完成/已投递。
- 原实现的发送记录保存调用方 `client_id`，未保留微信返回的实际 `message_id`，也没有记录响应中的 `ret` / `errcode`。原始响应无法事后还原；HTTP 200 和数据库 `delivered` 不能证明手机已收到。
- 不消费消息的 `getconfig` 检查确认：旧绑定返回 `errcode=-14`、`session timeout`；今天的新绑定返回 `ret=0` 和有效 typing ticket。旧绑定的过期不能作为新对话未收回复的根因。

## 确定的代码缺陷及修补

微信可能通过 HTTP 200 的 JSON `errcode` 报错。原适配器只检查可选 `ret`，所以 `{"errcode":-14}` 会被当成成功的空轮询，旧登录持续显示 ready。

产品提交 `da1124f` 在微信 HTTP 适配器中检查 `errcode`；`ret=-14` 或 `errcode=-14` 统一为不可重试的 `weixin.session_expired`，停止对应轮询并提示重新扫码。其他错误码和非法类型均不再被当成成功。保留缺省 `ret` 的有效协议兼容性，不把缺少消息 ID 当成重发理由。

发送响应仅记录调用方请求 ID、数字返回码是否存在及其值、消息 ID 是否存在、回执来源类别。正文、上下文令牌、账户身份、凭据和供应商 `errmsg` 不进入这些日志。有效 uint64 消息 ID 保存为字符串，缺省或无效 ID 保留稳定的调用方 ID。该记录仍是接口返回证据，不是手机接收 ACK。

参考：[Tencent iLink 类型](https://github.com/Tencent/openclaw-weixin/blob/main/src/api/types.ts)、[官方 API 实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/api/api.ts)。

## 验证与剩余结论

- 修改前新增的协议回归测试出现 20 个失败，覆盖被漏掉的错误响应和消息回执。
- 修改后本地及服务器独立候选目录均通过 142 项微信/渠道相关测试，包括取消和回收路径；严格 Pyright、Ruff、格式及差异检查通过。
- 上线仅覆盖两个生产文件及对应测试文件。模型、提示词、数据库模式和账户绑定不因该修补改变；候选以现有线上版本复制，其他源文件的 SHA-256 保持一致。
- **新会话未收到回复的原因仍待实际发送响应和用户接收反馈确认。** 不以旧绑定过期、模型更换、HTTP 200 或测试通过替代此结论。
- 不手动重发已被记录为投递成功的旧消息。下一次由用户发送唯一测试内容，再匹配接纳、生成、接口返回及手机反馈。

## 上线后的真实复测

[部署记录](weixin-no-reply-2026-10-05/deployment.json) 确认上线 `da1124f`：新微信绑定和 QQ ready，旧微信绑定准确显示 `weixin.session_expired`；QQ 原群以新成员观察恢复，同一成员集合、场景及发言授权保留。配置、凭据库及全部模型路由的散列/读回一致，未恢复数据库或手动发送微信消息。

用户发送“测试回复 0701”，并明确反馈仍未收到。该轮在北京时间 06:53:04.508 接纳，Opus 生成于 06:53:08.117 完成，06:53:08.420 返回发送结果。新日志实际记录 `ret=0`、无 `errcode`、无 `message_id`；仅发送一次，无生成或发送异常，回复为“这是什么暗号吗……我不太明白诶。”。见[逐轮证据](weixin-no-reply-2026-10-05/fresh-test.json)。

该复测排除了这一轮中“Opus 未产生答复”和“HTTP 200 携带错误码被忽略”的解释。官方协议也给出仅含 `ret=0` 的有效响应示例，所以 **缺少 `message_id` 本身不能证明投递失败或下行未入队**；用户未收到与接口接受必须分别保留。

## 重启后恢复的排查方向

用户补充，以前重新匹配似乎能恢复，故障似乎发生在后端重启后。

- 日志检索发现北京时间 05:22 和此次修补部署的 06:51 有启动过程；修改聊天模型的 API 仅保存路由，不重启 Runtime。此前旧响应的原始返回及手机接收时间没有足够证据，不能据此判定模型切换或某次重启是根因。
- 现有生命周期已经在连接开始调用 `notifystart`、结束调用 `notifystop`，请求格式与官方源码一致。对当前绑定重新调用启动通知返回 `ret=0`，`getconfig` 返回 `ret=0` 和有效票据；9 次发送使用了 9 个不同客户端 ID。见[生命周期探测](weixin-no-reply-2026-10-05/lifecycle-probe.json)。这些返回仍不能证明手机下行正常。
- 官方项目有相同“接口 `ret=0` 但手机未收到”的[用户报告 #310](https://github.com/Tencent/openclaw-weixin/issues/310)。它只是外部同类现象，不作为本项目根因或供应商风控判断。
- 已通过正常授权 API 准备一次新二维码，保留原有绑定与历史。待用户扫码并完成“重绑测试 0710”，先验收能否恢复，再决定是否进行同一绑定的受控重启对照；当前仍未宣布修复新会话的手机收信问题。
