具体来说：

```python
import asyncio

    await asyncio.sleep(2)
    print("ok_task 完成")  # 即使另一个任务抛异常，这里仍然会执行

    await asyncio.sleep(1)
    raise ValueError("出错了")

    try:
        results = await asyncio.gather(ok_task(), bad_task())
    except ValueError as e:
        print(f"捕获异常: {e}")
    # bad_task 抛异常后 gather 立刻向这里抛出
    # 但 ok_task 还在后台跑，不会被取消

```

### 关键点

1. **默认 `return_exceptions=False`**：第一个抛出的异常会直接传播给调用者，`gather` 的 `await` 处抛异常。

2. **其余任务不会被取消**：这是容易踩的坑。没完成的任务会变成"孤儿任务"继续跑，可能导致资源泄漏或意外副作用。

3. **如果设置 `return_exceptions=True`**：异常不会被抛出，而是作为返回值列表中的一个元素返回，所有任务都会跑完。

   ```python
   results = await asyncio.gather(ok_task(), bad_task(), return_exceptions=True)
   # results == ["ok结果", ValueError("出错了")]
   ```

           async with asyncio.TaskGroup() as tg:

               tg.create_task(bad_task())
       except* ValueError as eg:

Raft 中**领导者心跳超时**（或者更准确地说，**选举超时 / election timeout**）的计算方式大致如下：

### 两个关键定时器

1. **心跳间隔（heartbeat interval）**
   - 由 Leader 定期发送 `AppendEntries` RPC（即使没有新日志也发空的），用来维持权威、阻止 Follower 发起选举。
   - 通常设为一个较小的固定值，比如 50–150 ms，取决于网络延迟。

2. **选举超时（election timeout）**
   - 每个 Follower 各自维护。如果在这段时间内**没有收到**来自 Leader 的心跳或有效 RPC，就认为 Leader 已失效，自己转为 Candidate 发起新一轮选举。
   - 为了避免多个节点同时超时、同时发起选举导致**分票（split vote）**，每个节点的选举超时是一个**随机值**，通常从一个区间中均匀随机选取，例如 `[150 ms, 300 ms]`。

### 设计约束

Raft 论文给出了一个基本不等式：

```
broadcastTime ≪ electionTimeout ≪ MTBF
```

- **broadcastTime**：一次 RPC 往返时间（通常 0.5–20 ms）。
- **electionTimeout**：选举超时，需要远大于广播时间，以免正常心跳因网络抖动被误判为超时。
- **MTBF**（Mean Time Between Failures）：节点平均故障间隔，通常是数周或数月。

### 具体流程

1. Follower 启动时或每次收到合法心跳后，**重置**自己的选举超时计时器（随机值）。
2. 计时器到期仍未收到心跳 → 当前 term + 1，转为 Candidate，给自己投票，向其他节点发送 `RequestVote` RPC。
3. 如果本轮选举因分票失败（没人拿到多数），Candidate 会再次随机化超时后重试，随机化正是为了在下一轮中错开各节点的超时时刻。

### 简单总结

所谓"心跳超时"本质上就是 Follower 侧的选举超时计时器。它不是一个固定值，而是每次从 `[T, 2T]` 这样的区间里**随机取值**，核心目的是保证：
- 正常情况下 Leader 心跳远快于超时，集群稳定。
- Leader 真的挂了时，各节点大概率在不同时刻超时，减少分票，快速选出新 Leader。

在 Raft 中，**选举超时（election timeout）** 和 **心跳超时** 是两个相关但不同的概念：

### 心跳机制

Leader 会周期性地向所有 Follower 发送 **AppendEntries RPC**（即使没有新日志，也会发空的），这就是心跳。心跳间隔通常记作 `heartbeatInterval`，一般设为一个较短的固定值（比如 50–150ms，取决于实现）。

### 选举超时（Election Timeout）

每个 Follower 维护一个 **election timeout 计时器**。核心逻辑是：

1. Follower 每次收到合法的心跳（或有效的 AppendEntries / RequestVote），就 **重置** 这个计时器。
2. 如果在 election timeout 时间内 **没有** 收到任何心跳或合法 RPC，Follower 认为 Leader 已失联，转为 Candidate 并发起新一轮选举。

**计算与取值要点：**

- Election timeout 是在一个区间内 **随机取值** 的，例如 `[150ms, 300ms]`。随机化是为了避免多个 Follower 同时超时、同时发起选举导致 split vote。
- 每次重置计时器时，会重新随机一个值。

### 三者的约束关系

Raft 论文给出的经验不等式：

```
broadcastTime << electionTimeout << MTBF
```

- `broadcastTime`：一次 RPC 往返时间（通常 0.5–20ms）
- `electionTimeout`：选举超时（通常 150–300ms）
- `MTBF`：单节点平均无故障时间（通常数月）

`heartbeatInterval` 必须 **远小于** `electionTimeout`，这样在正常情况下 Leader 能在 Follower 超时之前发出多次心跳，避免不必要的选举。
