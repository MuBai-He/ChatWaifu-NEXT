# 个人信息整理：用户场景目录

研究日期：2026-10-12。状态：供产品讨论的场景假设，尚未开展用户访谈或需求频率统计。

本次结合官方产品文档、个人知识/工作管理方法、项目现有边界，以及用户“微信是主要信息源，希望整理长期记忆并发现重要遗漏”的目标，整理了 **42 个场景**。样例均为虚构，不来自真实微信聊天。

## 主要结论

用户最终希望得到三类结果：需要时找得到过去的信息；知道现在该做什么和还在等什么；在合适的时候获得提醒。长期记忆、任务、日程、提醒和参考资料需要分别表达，一条消息可以同时产生几类候选对象。

例如“周四晚上六点聚餐，我负责订位，小李不吃辣”可能形成：聚餐日程、订位任务、提醒候选、归属于小李的饮食偏好和原消息引用。后续一句“改到周五六点半”应更新原日程及提醒，不能再保留两份互相冲突的当前安排。

当前手机 App 已提供原文档案、线索、人工确认记忆和 OpenAI 兼容整理接口。下面列出的规划、日程联动、情境提醒等属于待评估需求，不代表已经实现。

## 第一轮优先验证的六条用户路径

1. **消息 → 有出处的任务**：识别确实由本人负责的请求或承诺，补全交付物、截止和状态。用户可确认、修改、拒绝，后续消息可提出完成候选。
2. **明确约定 → 日程与提醒**：识别时间、地点、人物，处理后续改期和取消；缺少确认的讨论保留为候选。准备任务、开始时间和提醒时间分别表达。
3. **等回复 / 等交付 → 跟进清单**：把自己待做和等待别人分开；允许用户设定何时再跟进，收到相关回复后提出关闭候选。
4. **值得保留的信息 → 确认记忆**：提取本人偏好、人物职责、项目背景、决定及理由，保留来源和有效期，支持更新、纠正和删除。
5. **资料 → 按人和项目找回**：保留链接、文件、版本和原消息入口。会前或被问及时找回相关材料，而非只给泛化摘要。
6. **每日简报 → 有限数量的关注项**：汇总今天安排、明确期限、个人承诺、等待事项和重要变化，区分确定信息与疑似遗漏，并允许调整筛选范围和提醒强度。

| 自由职业或个人接单 | 客户需求、报价与交付、确认记录、沟通对象、阶段跟进和报销材料     |
| 学生与学习者       | 课程和考试安排、作业与报名截止、学习计划、参考资料和复盘         |
| 家庭与日常生活     | 购物、快递、家人约定、学校通知、聚会、生日、续费和办事材料       |

## 容易被遗漏的十二类边界场景

| 边界                                   | 正确的用户体验                                               |
| -------------------------------------- | ------------------------------------------------------------ |
| 本人、他人、引用、转发和同名人物       | 先确定信息主体，不能把他人的偏好、任务或约会写给本人         |
| 提议、猜测、兴趣和真正承诺             | 保留候选或稍后考虑状态；不能把每句“有空看看”变成逾期任务     |
| 相对日期、时区、农历和模糊时间         | 根据原消息发生时间解释；无法确定时询问，保留原始时间表达     |
| 执行时间、硬截止、提醒时间             | 分别保存，避免只到最后一刻才提醒用户开始准备                 |
| 追加消息、改期、取消和事实变化         | 关联并修订同一事项；停止旧提醒，保留历史及修改出处           |
| 已读、已回复、已收到和已完成           | 这些状态分别表达；线下处理无法从聊天证明时允许用户确认       |
| 未送达提醒、已展示未处理、贪睡和关闭   | 显示状态差异；关闭或贪睡不自动等同于任务完成                 |
| 网络离线、设备休眠、重启和重复输入     | 恢复状态而非重复制造任务或提醒；过期提醒按用户策略处理       |
| 多来源同一事项、同标题不同事项         | 稳定来源标识、人物、时间和上下文共同判断，保留多份证据       |
| 资料缺失、媒体未下载和附件未解析       | 标明未读取的内容；不能仅凭文件名生成自称已阅读的结论         |
| 工作/生活/不同账户、敏感资料和忘记请求 | 来源和用途可选择；用户可纠正、限制保存范围或删除相应记忆     |
| 低重要性群消息、反复催促和用户已忽略   | 降低重复提醒，支持汇总、静默、忽略及恢复；反馈会改变后续筛选 |

## 哪些信息需要分别建模

| 对象               | 必要信息                                                | 核心状态区别                                   |
| ------------------ | ------------------------------------------------------- | ---------------------------------------------- |
| 原始资料           | 来源、作者/引用主体、原文、发生时间、采集时间、稳定标识 | 可用、缺失、变更；采集成功不等于内容已经理解   |
| 记忆候选与确认记忆 | 主体、事实类型、表述、证据、有效期、敏感性、确认来源    | 候选、已确认、已修正、已过时、已删除           |
| 任务与等待事项     | 负责人、动作、交付物、执行时间、截止、依赖、来源        | 待确认、待做、进行中、等待、完成、取消         |
| 日程               | 事件身份、起止、时区、地点、参与人、确认和修订来源      | 暂定、已确认、改期、取消、历史                 |
| 提醒               | 关联事项、触发条件、提前量、目标设备、重复和打扰策略    | 已安排、已展示、未确认送达、未处理、贪睡、关闭 |
| 规划与摘要         | 输入范围、时间预算、排序依据、推荐动作及引用            | 建议、用户接受/调整；不替用户制造外部承诺      |

这些是讨论用的产品对象，不是本次新增的代码协议。消息、记忆、任务和提醒有各自的生命周期，不能把同一条记录简单换个标签就认为完成了全部功能。

## 与 ChatWaifu 现有能力的关系

本地阅读了 `docs/plans/personal-assistant-integrations.md`、ADR 0057，以及当前任务和议程代码。项目已有个人日历/提醒接入、任务调度及送达状态相关结构；它们可以作为后续接入点。本次未重新检查服务器、真实账号或设备的部署状态，不把文档中的旧验收记录当作当前在线状态。

长期记忆沿用项目 memory-system 的分层、来源、策略、去重和纠正要求。日程和提醒继续有独立执行状态。原始聊天保留在资料层，提取出的结论保留来源，确认和授权通过适用的业务路径处理。

## 后续验证应回答的问题

- 用户最常遗漏的是自己的承诺、他人的请求、日程变更还是等待回复？不同用户可能排序不同。
- 用户愿意自动保存哪些类型的稳定事实，哪些需要每次确认？
- 哪些联系人、群和项目值得主动提醒？哪些只参与检索？
- 提醒应立即、按时还是汇总展示？什么反馈代表真正完成？
- 用户主要使用的日历、待办列表和提醒设备是什么，是否需要保持它们作为权威来源？
- 推荐计划需要哪些真实约束，例如可用时间、任务时长、不可移动的安排和专注时段？

本目录可以用于下一轮需求筛选与构建合成验收用例；目前不根据猜测直接改动用户日程、不创建实际提醒、不将新提取内容自动写入长期记忆。
