# Local Qwen3-TTS deployment on Tesla P4

> Historical deployment record from October 8, 2026. The service versions, release
> paths and QQ route revisions below describe that acceptance window. This
> documentation-only PR does not redeploy services or assert their current state.

Date: 2026-10-08. Server: `192.168.1.103`.

## Deployed behavior

The authenticated Runtime TTS registry now exposes `qwen3_tts_torch` as
`Qwen3-TTS · 绫地宁宁（本地 P4）`. The default remains `gpt_sovits`.
Selection is session scoped. Existing Runtime routing unloads the old provider
when no other session selects it and no active synthesis job uses it. Other
sessions retain their selected provider. Weights load on the first utterance.

This deploys the earlier isolated Qwen feasibility environment as a systemd user
service; it does not change Runtime or frontend source code.

## Runtime configuration

- Unit: `~/.config/systemd/user/chatwaifu-qwen3-tts.service`, enabled and active.
- Authenticated worker: loopback `127.0.0.1:8767`.
- Private worker environment: `~/.local/share/chatwaifu-server/qwen3-tts.env`.
- Model: `Qwen3-TTS-12Hz-0.6B-Base`, using the existing Nene reference recording.
- Environment: `/home/mubai/chatwaifu-server/probes/qwen3-tts-p4-20261007/venv`.
- Torch `2.7.1+cu118`, FP32, SDPA, CUDA device 0; lazy loading and offline weights.
- `native_streaming=false`: upstream returns a complete waveform.
- Four OpenMP/MKL threads; tokenizer parallelism disabled.
- `PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128` limits allocator fragmentation.
- Worker source snapshot and evidence:
  `/home/mubai/chatwaifu-server/workers/qwen3-tts-p4-20261008`.

The initial synthesis exposed a missing installed `qwen_tts` package: the old
probe had temporarily added its vendor source to `sys.path`. Installed that same
local vendor package without changing its dependencies. All 71 original package
versions remain unchanged; added worker/API dependencies stay in the isolated
Qwen environment. Installed worker files match the deployment source snapshot.

Registered the worker in `server.env` and restarted Runtime once. Existing
settings and the GPT worker registration were preserved; no schema migration.
The previous environment is privately backed up as `server.env.before` in the
deployment directory. Runtime source remains `releases/bubble-typing-20261007/source`;
the web release remains `releases/chat-clean-interface-20261008/web`.

## Acceptance evidence

- Worker regression suite: 14 passed. Runtime TTS tests: 20 passed using
  `--noconftest` because the local root bootstrap lacks unrelated `tiktoken`.
- Authenticated real worker synthesis: valid identity-scoped 24 kHz PCM WAVs.
  Final cold sample: 17.65 s for 2.96 s audio; warm: 7.64 s for 3.12 s audio.
- Production Runtime `WorkerTtsProvider` adapter synthesized a valid 3.20 s WAV
  in 7.93 s, including response identity validation.
- Two disposable Runtime sessions selected Qwen. Switching the first to GPT
  retained Qwen; switching the second unloaded it in 0.77 s. Test sessions closed.
- Before allocator configuration, model tensors were released but allocator
  reservation remained about 3.4 GiB. A diagnostic process confirmed no live
  Python CUDA tensors; synchronizing and clearing the FFT plan cache did not help.
- With the allocator configuration, final switch reduced reservation to 12 MiB
  and model device references became empty. Whole-GPU usage fell from 6605 MiB
  to 147 MiB; 7964 MiB became free. Small CUDA library/context allocations remain.
- Runtime health is `ok`, database `ready`; Runtime, GPT and Qwen units active.
  Qwen registry status is `ready`, model unloaded, GPT remains the default.

These are server synthesis, adapter and routing checks. Browser speaker playback
and long-utterance performance were not measured. First speech after unloading
pays model loading latency again. Existing generation cancellation regression
tests passed; native Qwen generation still has no immediate stopping hook.

## QQ recovery after deployment

The initial acceptance missed QQ group route state: Runtime restart at
2026-10-08 02:12 Asia/Shanghai paused both previously enabled groups with
`pause_reason=reconnect`, although the QQ transport itself reported ready.
This blocked new group admissions before LLM or TTS generation. The user reported
missing QQ replies afterward.

At approximately 03:11 Asia/Shanghai, fetched fresh authenticated audience
observations for both existing routes, checked exact account/member equality,
then re-enabled them through revision-checked operator APIs. Preserved participant
links, speaking grants, scene IDs, audience fingerprints and requested-voice
policy. Resulting revisions are 42 and 63. Readback confirms both routes enabled
with no pause reason. Evidence: private server `qq-route-recovery.json`.
No synthetic QQ messages were sent; fresh handset reply acceptance remains with
the user. Future planned Runtime restart acceptance must include group routes,
not only transport health, and revalidate the unchanged authorized audiences.

Raw JSON evidence and the final sample are in the deployment directory and the
local ignored `.local/validation/qwen3-tts-20261008/` directory. Credentials are
not included in the copied evidence.

## Rollback

Restore only the previous TTS worker registration in the current `server.env`
(preserve any subsequent unrelated edits), then restart Runtime. Disable and
stop `chatwaifu-qwen3-tts.service` after no session needs Qwen. The original
environment backup is available for comparison. Do not delete the model/probe
environment, which predates this deployment.
