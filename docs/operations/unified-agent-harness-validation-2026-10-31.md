```sh
.venv/bin/python tools/agent/harness_migration.py \
  --database /absolute/path/runtime.sqlite3 \
  --backup /absolute/path/backups/before-harness.sqlite3 \
  --report /absolute/path/backups/before-harness-report.json
```

实际切换时停止新触发、核对在途写入，再停止 Runtime 并迁移。核对确认记录、来源映射、提醒规则和处理权水位。回退保留行动账本，先查明远端效果；数据库还原不能撤销已发生的日历操作。

## 11 月 1 日：大量保存与 SQLite 竞争优化

用户提出大量保存慢与 database is locked 风险。当前手机与正式 Runtime 日志未捕获该错误，手机业务库实际为 WAL；外部 sqlcipher 只读诊断连接的 busy_timeout=0 不是 Android 应用连接的设置，不能据此认定 App 没有等待策略。Runtime 已有单连接串行事务、BEGIN IMMEDIATE 与 5000 毫秒 busy_timeout，本轮未修改服务器存储实现或配置。

代码确有两项风险：只读批量预览申请写事务，以及嵌套确认在外层事务内逐条唤醒同步。原先每次 new MemoryStore 也分别维护 helper/连接池。改为同进程按规范化数据库路径共享有引用计数的 helper，关闭一个使用者不会提前关闭其他仍存活的任务；维持 WAL 和原 schema 6。业务写事务改为 beginTransactionNonExclusive；批量预览只冻结数据，真正提交仍重新核对当前建议、出处、修订、权限和事项状态，不拆分最多 100 条的原子确认。

嵌套保存延迟通知，最外层成功提交后只调度一次同步，不在持锁期间调用 JobScheduler/前台服务。临时 SQLiteDatabaseLockedException/SQLiteTableLockedException 单独归类 storage_busy，失败清理仍占锁时保留持久租约恢复；这些情况不算模型失败、不耗尽来源的五次错误额度。没有承诺其他进程可以永远不占锁，也没有把模型或外部副作用的未知结果直接重试。

旧源码对照的两项新增用例均失败：预览等待写者超时，批量同步通知不满足一次/提交后约束；恢复新源码后通过。现有套件扩展至 103 项，覆盖 100 条末尾注入失败后全部回滚、重新确认成功、拒绝重复确认、跨使用者关闭、保存时出处/修订变化以及 storage_busy 不增加模型失败次数。Debug/Release 构建和双 Lint 通过。

原旧版 Flow 默认组合夹具仍含 schema 4 及跨会话混合批次的旧预期，试跑不能作为当前版本通过证据。保留失败记录，最终撤回无关的旧夹具改写，仅在现有 FlowInstrumentation 增加针对当前 schema 的 storage_only 场景。小米 USB 真机在命名隔离库中通过 8 项存储断言：写者占用时预览 100 条可读、关闭并行使用者后库仍可用、最后一条失败整体回滚、全部待确认保留、100 条提交后恰好保存一次、重复提交被拒绝。小样例提交耗时 306 毫秒，不含网络和页面重绘；不是对所有正文大小/设备状态的性能保证。两次旧默认夹具试跑后均恢复原签名 Release；最后的定向验收也已恢复 Release。

安装为所有者签名 0.6.3 / code 24，正式数据不导入测试库。升级前保护快照中的 187 条确认记忆、12 条事项、286 条待核对建议及原连接设置均逐条相同；后台新增建议可保留，不拿全表数量变化冒充损坏。无线调试中断后通过同机 USB 继续，恢复与保全证据位于 `.local/artifacts/sqlite-save-contention-20261101/`。没有改变 Google 日历、提醒规则或正式 Runtime 的整体发布状态。

实现依据：[Android SQLiteDatabase 事务与 WAL](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase)、[SQLite WAL 官方说明](https://sqlite.org/wal.html)。这些机制允许读写并发但不允许多个写者同时提交，因此必须缩短写事务并协调连接生命周期。
